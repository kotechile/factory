### 1. The Bottleneck & Market Context
- **Current State:** As of 2026-09-01 every French VAT-registered business must be able to **receive** structured e-invoices, and large + intermediate-sized enterprises must **issue** them; PDF/paper is no longer compliant for in-scope B2B flows. Only Factur-X (PDF/A-3 + embedded CII XML), UBL 2.1 and standalone CII are accepted, at the EN 16931 profile or above, plus the **CIUS-FR** overlay (SIRET for both parties, French VAT category mappings, extra cardinality). The failure mode is not the concept — it is the mechanical gap between what an ERP emits and what a platform accepts: PDF libraries default to the MINIMUM/BASIC profiles that are *illegal* under the mandate; ERPs export the trade name where `cac:AccountingSupplierParty/cac:Party` needs the registered legal name (BR-06); currency is rendered as "Euro"/"€" instead of ISO 4217 `EUR` (BR-05); issue dates arrive as `DD/MM/YYYY` and fail XSD date validation (BR-03); templates hard-code a stale specification identifier in `cbc:CustomizationID` (BR-01); and totals drift to the cent across lines, VAT breakdown and grand total (BR-CO-*). Today the only pre-send checks available are per-invoice web validators — they *find* the failure, they do not **fix** it, do not emit the corrected artifact, and are not callable by an agent mid-pipeline. The same mechanics repeat for every 2026 mandate (Poland KSeF FA(3) with VAT rounding only at total, Belgium Peppol BIS 3.0, Germany XRechnung/ZUGFeRD 2027), so one deterministic rule engine covers a multi-year, multi-country surface.
- **Validation Intensity:** High and quantified. Ten named rules (BR-01/03/05/06/07 and the total-reconciliation family) are documented as the dominant rejection causes across thousands of validations; "PDF library defaults to MINIMUM/BASIC" is called one of the top three integration failures on real pipeline traffic; the penalty escalation to €50/invoice with annual caps is a published change; and 15+ independent guides, PA/PDP vendors and country pages in the window restate the same format/profile/CIUS requirements. This is a repeatable structural pain with a hard, dated trigger — not a one-off complaint.

### 2. Architecture & Technical Blueprint
- **Engine Type:** Schema Transpiler + Validator (archetype **b**) — canonical invoice model → compliant XML, plus a rule engine over XML.
- **Deterministic Core (`src/lib/calc/einvoice/`):**
  - `types.ts` — BT/BG-grouped invoice model: `seller/buyer {name, legalName, vatId, siret, country, address}`, `invoice {number, issueDate, currency, lines[{description, quantity, unitPrice, vatCategory, vatRate, lineNetAmount, allowances/charges}], paymentTerms, dueDate, references}`, plus `targetFormat`, `targetCountry`.
  - `rules/en16931.ts` — rule implementations keyed by stable rule id, ordered by measured frequency: `BR-01` specification identifier present and version-correct, `BR-03` issue date as ISO 8601, `BR-05` ISO 4217 currency, `BR-06`/`BR-07` seller/buyer legal name, `BR-CO-10…15` reconciliation (Σ line net = invoice net = total excl. VAT; VAT breakdown per category+rate = VAT total; grand total = net + VAT), `BR-CO-25` payment terms or due date, card/unit/quantity consistency, VAT category ↔ rate coherence. Every finding carries `{ruleId, severity, fieldPath, message, fix}`.
  - `rules/ciusFr.ts` — CIUS-FR layer: SIRET present and 14-digit Luhn-valid for both parties, French VAT identifier format + VAT-key formula (`FR` + 2-char key + 9-digit SIREN), French tax-category mappings, French cardinality constraints; detects and blocks the profiles that are illegal for the mandate (MINIMUM, BASIC WL, BASIC).
  - `emit/facturx.ts` / `emit/ubl.ts` — serializer producing CII XML at the EN 16931 profile (and the `EXTENDED-CTC-FR` target carrying the fields a Plateforme Agréée needs for lifecycle reporting to the DGFiP) or UBL 2.1, with the correct `cbc:CustomizationID`/`cbc:ProfileID` for the chosen flavour.
  - `reconcile.ts` — the invariant that earns trust: totals reconcile to the cent and are reported explicitly (`delta`), country rounding rules respected (e.g. Polish VAT rounding only at the total, not per line). Any unmapped required field fails loudly with the rule id — **no silent fallback**, no invented default.
  - `score.ts` — 0–100 pre-send readiness score with blocking vs advisory findings.
- **Inputs / Outputs:** `POST { seller, buyer, invoice, targetFormat, targetCountry }` → `{ valid, score, findings[{ruleId, severity, fieldPath, fix}], emitted: { format, xml }, reconciliation: { lineNetSum, taxExclusive, vatByBreakdown[], grandTotal, delta } }`. Also accepts an existing XML/PDF-hybrid upload to be validated as-is (read layer).
- **Known-answer test vectors (`vitest`):** one fully valid EN 16931 fixture (expect `valid:true`, score 100, delta 0) plus broken fixtures per rule — missing seller name, `"Euro"` currency, `21/04/2026` date, BASIC-profile document, stale `CustomizationID`, and a totals-off-by-one-cent case — each asserting the **exact** finding list, not just a boolean.
- **Known limit (stated, not hidden):** EN 16931 is ~1,300 rules; v1 implements the measured high-frequency core (the top rule families above) and reports the rest as `unsupported-rule` rather than implying full coverage. PDF/A-3 container authoring is **P1**; v1 emits standalone CII/UBL XML, which platforms and PAs accept.

### 3. Dual-Pronged Monetization
- **Web Tier (Stripe):** free single-invoice validation with the readiness score and blocking-rule list; **$9 one-off fix pack** (corrected XML + change list for every finding); **$29/mo** batch tier (multi-invoice, multi-country profiles, saved rule exceptions) aimed at ERP integrators, bookkeepers and agencies. Comfortably clears the $0.25/query margin floor.
- **Agentic Tier (WebMCP):** `validate_einvoice(xml|invoice)` at **$0.10/call**, `convert_invoice_to_facturx(invoice)` at **$0.25/call**, `check_eu_vat_id(id, country)` at **$0.05/call**, Stripe-metered. This is the differentiated layer: an AP-automation agent validates before submission instead of discovering the rejection downstream, and an ERP copilot emits a compliant artifact without a human opening a validator page. The free web validators are UI-first and expose no metered agent contract.

### 4. Zero-Friction Viral Hook
- **Rejection-Risk Scorecard:** a shareable `?doc=` (base64 invoice payload) deep-link showing the 0–100 readiness score, the blocking rule list and the fixed XML diff. Bookkeepers circulate it to clients the way they circulate a tax summary.
- **Embeddable badge:** "EN 16931 ready — 98/100 · 0 blocking rules" as an `<iframe>`/web component that ERP vendors drop into their invoice preview screen; every embed carries branded attribution → backlink + signup.
- **pSEO surface:** one public page per rejection rule and per country/format combination (`/facturgate/calc/br-06-seller-name`, `/facturgate/calc/cius-fr-siret`, `/facturgate/calc/ksef-fa3-…`), which is exactly the long-tail the existing pSEO machinery was built for.
