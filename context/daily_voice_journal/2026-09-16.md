  `06:11:28,728 Job 'Full Pipeline: gpu_hardware' completed successfully` → `06:12:25,292 delivered to
  slack … message_id=1789539145.156189` → `06:12:25,613 ERROR cron.jobs: Timed out waiting for local
  fire fence /root/.hermes/cron::923a4f478c2f; failing closed` → `06:12:25,614 WARNING Job …: fire claim
  ownership lost; interrupting stale run` → execution row written
  `status=failed, error="Interrupted by shutdown before terminal completion."`.
  **The run did not fail.** The agent finished its turn and Slack received the report; only the
  terminal ledger write failed. Mechanism: `cron/jobs.py::_fire_job_lock` is a per-job in-process
  `threading.RLock` acquired with a **30 s** timeout (`_JOBS_LOCK_TIMEOUT_SECONDS = 30.0`), and the
  docstring states it "may be held across network delivery" — the delivery-handoff thread holds the
  fence for the whole Slack post while the terminal write waits, times out, fails closed, and
  `_record_fire_ownership_lost` writes a false failure over an already-successful run.
  Evidence of scale: **18 occurrences since 2026-09-03 across 8 distinct days** (09-03 ×4, 09-04 ×3,
  09-05 ×2, 09-07, 09-13, 09-14, 09-15, 09-16), hitting the daily sweep, the Build Watchdog and every
  Full Pipeline job. **Zero** of them are the file-lock variant (`Timed out waiting for fire fence` —
  0 occurrences); all 14 in `errors.log` are the in-process RLock. Consequences: `hermes cron list`
  reports healthy jobs as failed, `delivery_outcome` is left `NULL` on the ledger row although the
  message was delivered, and **no incident is raised** (0 open) because the failure is written as a
  job-run status, not an incident class — so the fleet's own monitoring never sees it.
  Fix direction (for the Hermes fork, not this repo): either don't hold the per-job fence across the
  network post, or make the terminal write retry/nest instead of fail-closed, or refuse to overwrite a
  `success` terminal state with an ownership-lost failure. The Hermes-side skill
  (`~/.hermes/skills/autonomous-ai-agents/hermes-cron-debugging`, not a file in this repo) already
  documents this exact defect and its one-line fix — and the fix was **absent from the tree**:
  `cron/jobs.py::heartbeat_fire_claim` still wrapped the refresh in `_under_fire_fence(...)`, and the
  gateway (started 2026-09-12 15:13, after the local patch at 15:12) ran that code. The patch has been
  re-applied this sweep (`cron/jobs.py.bak.20260916` backup; `pytest tests/cron/` re-run) and takes
  effect on the next gateway restart — deliberately **not** restarted mid-run, since the cron
  scheduler runs in-process with this sweep. Skill reference updated with the post-refactor code shape.
